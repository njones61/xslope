# Stage 1 (LEM Engine) Pre-Publication Audit — Synthesis Report

## 1. Overall Verdict

The xslope LEM engine is **largely sound in its core formulations but carries two genuinely validity-critical defects that must be fixed before publication**: (a) `janbu()` does not implement the Janbu Simplified Method at all — its base FS is byte-identical to OMS and is merely multiplied by the `f0` correction; and (b) the force-equilibrium family (`corps_engineers` default and `lowe_karafiath`) mishandles the interslice-angle sign convention on right-facing slopes and selects/labels a non-conservative default, in one case flipping an unsafe slope (FS<1) to apparently safe. By contrast, `oms()`, `bishop()`, and `spencer()` are confirmed correct — independently reproduced to 6–13 significant digits, including the phi=0 OMS=Bishop=Spencer identity. The shared `force_equilibrium()` *engine* itself is mathematically correct; every problem is in the convention/sign/root-finder layer that wraps it. Net: the moment-based methods are publication-ready; Janbu and the force-equilibrium methods need fixes and documentation corrections first.

## 2. Confirmed Findings, Ranked by Severity

### VALIDITY-CRITICAL

**F1. `janbu()` base is OMS, not Janbu** — method `janbu`, `solve.py:433-446`
- **Defect:** Base FS uses the Fellenius normal `N = W·cosα − u·dl` (no `m_alpha`, non-iterative) with an OMS driving denominator `ΣW·sinα`. This is OMS exactly; the only thing distinguishing `janbu()` output is the `f0` multiplier. True Janbu Simplified needs Bishop's iterative `m_alpha` normal and a horizontal-force denominator `ΣW·tanα`.
- **Evidence:** Arai & Tagyo: `janbu_base = 1.342500 = oms() 1.342500`, diff `0.000e+00`; denominators `ΣW·sinα = 2558.57` vs standard `ΣW·tanα = 3480.15` (ratio 0.735). ACADS Simple: `0.942029 = oms() 0.942029`. Reproduced by hand and from scratch by the adversarial verifier.
- **Fix:** Replace with Bishop's iterative effective normal `N'`, iterate F to convergence, use the `ΣW·tanα` force denominator, then apply `f0`. Local to `janbu()`; no other method affected.
- **ESCALATE: changes published numbers** — every reported Janbu FS will change (e.g. Arai base 1.3425 → materially lower true-Janbu value).

**F2. `janbu()` has no F-iteration** — method `janbu`, `solve.py:446`
- **Defect:** Single closed-form pass with no convergence loop — a direct symptom of the dropped `m_alpha` term. (Same root cause as F1; listed separately because it is the structural tell.)
- **Evidence:** On `method_slices_problem` (c-φ, 20 slices): code base `1.2994 = OMS 1.2994` to 1e-9; from-scratch `m_alpha`-iterated Janbu = `1.6615` (7 iters), a 21.8% underestimate. Cross-checks: problem2 base 1.2897 vs 2.0183; eight_layers 2.3735 vs 2.6452.
- **Fix:** Introduce the F-iteration loop mirroring `bishop()` but with the Σ-force denominator. **Fixing F1 fixes F2.**
- **ESCALATE: changes published numbers.**

**F3. Corps default variant (v2) is non-conservative and can flip unsafe→safe** — method `corps_engineers`, `solve.py:665-681`
- **Defect:** The shipped default `variant=2` is systematically the least-conservative method available; docstring (line 641) and `force_eq.md` (line 242) wrongly call it "the safer default."
- **Evidence:** `simple_foundation` critical circle: Spencer=Bishop=OMS=`0.96539` (unsafe), Corps v2 = `1.13656` (+17.7%, reported safe), v1 = `1.05913`. Ordering v2>v1>Spencer in all 6 benchmarks; v2 over-predicts Spencer by 3.5–17.7%.
- **Fix:** Stop labeling v2 "safer"; warn it is the least conservative. Flipping the default to v1 is **not** clearly correct (trades FS-value non-conservatism for search-exploitation risk on v1's fixed steep angle) — adopt the wording/warning fix and document, rather than silently switching.
- **ESCALATE if default is changed: changes published numbers** (e.g. sloping_bottom 1.358→1.311).

**F4. Corps v2 omits the right-facing sign flip → asymmetric, wrong on right-facing slopes** — method `corps_engineers`, `solve.py:665-686`
- **Defect:** v2 builds per-boundary `theta = degrees(arctan(signed ground slope))` with no facing correction, while the structurally identical `lowe_karafiath` applies a `right_facing` flip. Since `force_equilibrium` marches left→right and the interslice term is sign-sensitive, v2 is wrong-signed on right-facing slopes.
- **Evidence:** `simple_embankment` mirrored: Corps `1.392673` (left-facing) vs `1.196437` (mirror), 18% asymmetry, while every other method is symmetric to ~3e-5. On right-facing `method_slices_problem`: Corps v2 = `1.2443`, falling **below OMS 1.3026** (impossible ordering); v1 = `1.6201` restores OMS<Janbu<Bishop≈Spencer<Corps<Lowe. Monkeypatching the lowe-style flip yields mirror FS `1.392719`, matching the original.
- **Fix:** In the `variant==2` branch detect `right_facing = y_lt[0] > y_rt[-1]` and negate `theta_list` accordingly (mirror `solve.py:738-741`), or factor the shared theta-assembly so corps and lowe use one implementation.
- **ESCALATE: changes published numbers** for any right-facing Corps-v2 result.

**F5. `lowe_karafiath()` double-flips theta on right-facing slopes → FS exceeds Spencer** — method `lowe_karafiath`, `solve.py:737-741`
- **Defect:** The `right_facing` branch negates theta even though theta is already computed from signed ground/base slopes — a spurious double sign flip, producing an unconservative FS that exceeds the rigorous Spencer value (impossible for a force method).
- **Evidence:** `method_slices_problem`: LK `1.6417` vs Spencer `1.5788`, Corps `1.2420`; problem2: LK `2.1016` vs Spencer `1.9418`; earth_dam_down: LK `1.5699` vs Spencer `1.5600`. At interface 15, LK theta `+25.797°` where the signed-correct value is `−25.797°`. Removing the negation gives `1.2669 / 1.5706 / 1.3215`, correctly bracketed below Spencer. Left-facing results unaffected (branch never executes; acads_simple LK `1.4749` unchanged).
- **Fix:** Delete the `right_facing` branch; assign `theta_list[j] = degrees(arctan(avg_slope))` directly, matching `corps_engineers`. Safe for left-facing (byte-identical).
- **ESCALATE: changes published numbers** for right-facing LK results (these are wrong today and should change).

> **Note on F4 vs F5 — opposite directions, same fix family:** Corps v2 is *missing* a flip it needs; LK *applies* a flip it shouldn't. The clean resolution is to make both use the **signed** ground/base slopes directly with no facing negation (delete LK's branch; do **not** add a raw facing flip to Corps but instead ensure Corps v2 uses the signed slope consistently). Norm should treat these as one coordinated change to the shared interslice-angle convention to avoid them cancelling or diverging. (The cross-method battery's proposed "add the lowe-style flip to Corps" and the LK finding's "delete the flip from LK" must be reconciled — both reach a consistent signed-theta convention, but applied naively they describe opposite edits. Recommend: standardize on signed theta with no negation everywhere.)

### WRONG-BUT-BOUNDED

**F6. `force_equilibrium` Newton diverges from fixed guess 1.5 when true FS≪1.5** — method `corps_engineers`/`lowe_karafiath` engine, `solve.py:614` (guess at `510`)
- **Defect:** Shared root finder uses derivative-free secant from a single fixed `fs_guess=1.5`, no bracket/fallback. Residual is monotone and flat above the root, so a low true FS makes the secant walk onto the flat tail and diverge (~1e32), returning a spurious "failed to converge."
- **Evidence:** acads_simple, phi=0/c=20: valid root `FS=0.72186` (brentq) but `corps_engineers` variant=1 returns FAIL with "Tolerance of 1.33e+32 reached." `dResidual/dFS = −350` at FS=1.5 vs `−1519` at root; seeding newton at 0.8 converges to 0.72186.
- **Fix:** Bracketed solver (brentq over e.g. [0.1, 10]) or low seed + bracketing fallback; keep graceful handling when genuinely no physical root exists. Fails loudly today (no silent wrong answer).
- No published benchmark changes (current benchmarks converge).

**F7. Corps v1 takes `abs()` of chord inclination, discarding facing sign** — method `corps_engineers`, `solve.py:662`
- **Defect:** `theta_deg = abs(...)` forces positive inclination even where the signed chord is negative (engine's primary descending orientation), so v1 and v2 assign opposite-signed theta to the same geometry; ~6% FS spread from the sign error alone.
- **Evidence:** 2-slice right-facing toy: signed chord `−16.699°`; feeding `+16.699` vs `−16.699` directly to `force_equilibrium` gives `1.749465` vs `1.653897` = **5.78%** spread. Left-facing benchmarks unaffected (chord already positive, abs() a no-op).
- **Fix:** Remove `abs()`; use signed `arctan2`. (Reconcile with F4/F5 signed-theta standardization.)
- May change right-facing Corps-v1 numbers; left-facing published numbers unchanged.

**F8. Janbu `f0` parabola turns over for deep surfaces** — method `janbu`, `solve.py:483`
- **Defect:** `fo = 1 + b1*(dL − 1.4*dL²)` peaks at d/L=0.357, decreases beyond, returns to 1.0 at d/L=0.714, goes negative further out; `d/L` is geometrically unbounded and unguarded.
- **Evidence:** g(0.357)=0.1786 (max), g(0.5)=0.1500, g(0.6)=0.0960; toy at d/L=0.4118 gives fo=1.0872 (past peak). Repo benchmarks safe (ACADS d/L=0.134, Arai d/L=0.202).
- **Fix:** Clamp/saturate d/L at the chart domain (~0.357 peak) and warn when exceeded. Latent — does not affect current V&V.

### LOW / COSMETIC

**F9. `theta_p` units contract mismatch** (LOW) — `oms`/`bishop`/all methods, `solve.py:184,213,243-244` vs docstring 138-145; storage `slice.py:1247`. Methods consume `theta_p` in **radians** while docstring lists all other angles in degrees and never notes the exception. Correctness relies solely on `slice.py:1247` storing `radians()`. Evidence: pile moment `−720.55` (deg, wrong) vs `+829.31` (rad, correct). Fix: document that theta_p is stored/consumed in radians (lower-risk than re-standardizing, which must touch every method + storage simultaneously or double-convert). No benchmark change.

**F10. OMS right-facing auxiliary-moment sign convention** (wrong-but-bounded, latent) — `oms`, `solve.py:217,229,233,237`. Only the **distributed-load** moment arms (`a_dx`, `a_dy`) are sign-broken for right-facing slopes; `kw` and `T` are **correct** (they track facing via the sliding-direction convention). Evidence: right-facing D-moment code `+132405.2` vs physics `−132405.2`; an upslope crest surcharge wrongly *raised* FS 1.3026→1.3333. Fix: multiply **only** the D arms by the `right_facing` sign — do **not** touch `a_s`/`a_t`. Latent (no shipped right-facing benchmark has a distributed load).

**F11. `single-guess-secant` produces a genuine-but-spurious high root on submerged phi=0** (corrected severity HIGH per verifier) — `force_equilibrium`, `solve.py:614`. On `submerged.xlsx` (phi=0) OMS=Bishop=Spencer=`1.1524` but Corps/Lowe return `~6.39 / ~3.65` as **success=True** with no warning — a 3×–5.7× non-conservative FS. Critically, 6.39 is the *genuine and only* root of the force-equilibrium equations (brentq returns the same), so **bracketing does NOT fix this** — it is a formulation limitation of force methods for phi=0 + dominant vertical (ponded) load, distinct from F6. Fix: warn/guard for phi=0 + dominant-vertical-load configurations in force methods; document the limitation. Worth escalating to Norm as a correctness caveat despite being a "method limitation."

**F12. Janbu `b1` exact-float branch** (cosmetic) — `solve.py:472-480`. Global classification by exact `==0` on summed phi/c. The global convention is *correct* Janbu practice; only the exact-equality and undocumented mixed-soil behavior are weak. Worst-case misclassification ≈3–6% f0 error under contrived inputs. Fix: tolerance-based branch + document. No benchmark change.

**F13. Janbu `d` from base-center points** (cosmetic, no-op) — `solve.py:460-467`. d sampled at slice base centers, which lie *exactly on* the surface; error vs analytic max is 0.034%/0.005% → fo error ~0.001%. The proposed LineString fix is **no better** (sometimes worse). Recommend: do nothing.

**F14. Spencer non-convergence on design2 stored circle** (cosmetic) — `solve.py:951-1158`. Hard non-convergence on a 74° near-vertical base slice; independent residual scan confirms **no joint Spencer root exists** (R1/R2 surfaces never coincide). Bishop converges (0.9937). Correct/defensible behavior. Fix (optional): document in spencer.md; surface best-residual with a warning. No code change required.

**F15. Spencer unnormalized residual tolerance** (cosmetic) — `solve.py:971`. Single absolute tol=1e-4 applied to force residual R1 and moment residual R2 (different units). Never bites: at convergence R1=1.46e-11, R2=1.12e-08 (earth_dam_down). Proposed normalization is itself hazardous (ΣQ→0). Recommend: no change.

**F16. Stale docstring column names** (cosmetic) — `force_equilibrium` docstring `solve.py:522-526`. Docstring lists `'d'` as distributed load, but code reads `'dload'` (`solve.py:552`); a real `'d'` column exists meaning rapid-drawdown strength (`slice.py:1264`) — actively misleading collision. Pile cols `h_pile`/`theta_p` undocumented. Fix: rename in docstring; documentation-only.
